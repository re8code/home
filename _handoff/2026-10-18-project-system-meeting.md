# 회의록 — 프로젝트 관리 시스템 (훈련생 ~ 에이전트)

- 일시: 2026-10-18
- 장소: `home` 저장소 세션 (논의만 — 이 저장소의 사이트 파일은 건드리지 않음)
- 참석: 원장(사용자), Claude
- **이 문서는 임시 보관본이다.** 프로젝트 관리 시스템의 저장소가 생기면 사용자가 그쪽으로 옮긴다(`_handoff/`는 `_` 접두사라 GitHub Pages 배포에서 제외된다). 새 저장소의 첫 세션은 이 문서를 읽고 시작한다.

---

## 0. 배경

- `home`은 대문 랜딩 1장에만 집중한다. 학습 콘텐츠 등 상당 부분은 `student` 저장소로 옮긴다(기존 결정 ADR D6 · `docs/PRD.md` §9 · `docs/DEV_PLAN.md` Phase 5 — 이 방향이 바람직하다고 재확인).
- 데이터는 `recode-db`(Supabase 통합 DB, wonoj=`public` · recodemate=`class`, 앞으로 `core` 등)에서 진행한다. wonoj·recodemate DB 통합은 2026-10-17 완료.
- 훈련생부터는 **한 사람이 실전형 프로젝트를 혼자 진행**한다 = **바이브 코딩**. 틀 없이 진행시키면 에이전시가 관리할 수 없으므로, 작업의 틀을 강제하고 그 안에서 진행·방향을 모니터링하는 시스템이 필요하다.

## 1. 핵심 결정

### 1-1. 틀 = 원장의 문서 체계

원장이 형제 저장소들에서 쓰는 체계(PRD · ARCHITECTURE · DEV_PLAN · DEVLOG · tasks/ · report/ · `vX.XX` 커밋)를 **에이전시 표준 템플릿**으로 굳혀, 모든 프로젝트를 그 위에서 시작한다. 이 틀은 바이브 코딩을 통제하는 장치이며, 틀대로 일하는 것이 곧 훈련이다.

### 1-2. 분할선 — 문서 소유권이 등급에 따라 내려간다

요구사항 분석 → 기술 스택 → 개발 플랜까지는 에이전시가 구성하고, 실제 작업은 개인에게 할당한다. 등급이 오를수록 학생이 소유하는 문서가 한 칸씩 위로 올라간다.

| 등급 | 눈금 | 학생이 소유 | 에이전시 |
|---|---|---|---|
| 훈련생 | 동행 | **task 분해** + 실행 | PRD · 스택 · DEV_PLAN 확정 |
| 랜서 D | 동행 | + DEV_PLAN 초안 | PRD · 스택, 플랜 승인 |
| 랜서 C | 위임 | + 기술 스택 제안 | PRD, 스택·플랜 승인 |
| 랜서 B | 위임 | + PRD 초안 | 전체 승인 |
| 랜서 A | 책임 | 전부 초안 | 승인만 |
| 에이전트 | 단독 | 전부 | 사후 검증 |

- 이것이 `agency` PRD §3에 "구체 미정"으로 남아 있던 **눈금(동행→위임→책임)**의 구체안이다.
- 초안에서는 task 분해를 랜서 D부터 넘기려 했으나, DEV_PLAN을 "무엇을·언제까지"만 고정하기로 하면서(§1-9) **훈련생이 처음부터 task 분해**를 하도록 한 칸씩 당겼다.
- **분할선 조정: 등급이 기본값, 프로젝트별로 위로만(에이전시가 더 쥐는 방향) 조정 가능.** 아래로는 불가.

### 1-3. 배정

- 훈련생 ~ 랜서 A: **에이전시가 배정**.
- 에이전트: **본인이 선택** — 공지 보드 + 제안서 → 에이전시 선정. 미선택 프로젝트·중복 선택·에이전트가 데려온 고객(역제안)도 이 구조로 푼다.
- 랜서 A는 공지 보드 열람 + 연습 제안(선정 대상 아님, 평가 대상).
- 에이전트가 나오기까지 시간이 걸리므로 공지 보드·제안은 **나중에 만든다**. 대신 배정에 "방식" 칸(에이전시 배정 / 제안 선정 / 역제안)을 처음부터 두고, 분할선·권한은 등급 값에서 계산하게 해 둔다.

### 1-4. 하나의 시스템

- 훈련생부터 에이전트까지 **하나의 시스템**에서 관리·사용한다. 승급은 등급 값 변경이며 데이터 이관·내보내기는 없다.
- ⚠️ `agency` ADR **D7**(2026-09-17, 칸마다 별도 사이트·회원 시스템, 승급 = 내보내기, 에이전트 관리는 별도 프로젝트로 이관)과 충돌 → **D7 개정 필요**(§6).
- ⚠️ `recode-db`의 서비스↔등급 표에서 "훈련 서비스(train)"와 "실전 운영 서비스(work)"를 나눈 것도 사실상 등급으로 나눈 것 → 프로젝트 관리는 **하나의 서비스**로. 단 계약·정산·민감정보는 별도 스키마·엄격한 권한.

### 1-5. 프로젝트 종류

| | 훈련 프로젝트 | 실전 프로젝트 |
|---|---|---|
| 대상 | 훈련생 | 랜서 · 에이전트 |
| 원천 | 실전 클론 · 에이전시 과제 · **본인 기획** | 실제 고객 |
| 고객 | 없음(에이전시가 고객 역할) | 있음 |
| 계약·수익 | 없음 | 기본 계약 + 부속서, 수익배분 |
| 틀·보드·관찰 기록 | 같음 | 같음 |

- 훈련생은 **실제 고객 프로젝트에 투입하지 않는다.** 실제 프로젝트를 클론·모방해 훈련에 쓸 수는 있다.
- 실전 클론은 고객 식별 정보·실데이터·원본 자료·비밀값을 제거(익명화)하고, 고객 계약에 "익명화 교육 재사용" 동의 조항이 있는 것만 쓴다(`business` 쪽 고객 계약서 몫).
- **본인 기획**: 훈련생이 기획 제안 → 에이전시가 협의해 PRD·스택·플랜 확정(분할선 유지). 결과물 권리는 **훈련생**에게 있고 종료 시 저장소를 훈련생 계정으로 이전. 등록 약관에 명시.

### 1-6. 졸업 과제와 관문

- 훈련생의 마지막 프로젝트 = **졸업 과제**, 원천은 **실전 클론만**.
- 원본 실전 결과물을 기준으로 "실제 납품 가능 여부"를 평가. 진행 중 에이전시가 최소 1회 가상의 고객 요구 변경을 넣는다.
- 관문(훈련생 → 랜서 D) = 졸업 과제 평가 + 전 과정 관찰 기록.
- 불합격 시 **다음 기로 넘어가 재도전**, 수업료 추가 납부(recodemate 몫). 재도전은 **다른 클론 과제**. 평가는 기 종료 전에 마친다.

### 1-7. 승급

- **모든 승급은 에이전시(원장)가 결정**한다 — 학생 → 훈련생 포함.
- 승급 처리는 에이전시 화면 한 곳. 근거는 각 서비스의 기록(student의 학습·관찰 기록, 프로젝트 시스템의 평가)을 모아 본다. 결과는 `core.grade_history`.

### 1-8. 서비스 ↔ 등급

| 서비스 | 학생 | 훈련생 | 랜서 | 에이전트 |
|---|---|---|---|---|
| Online Judge (wonoj) | O | X | X | X |
| Class (recodemate) | O | O | X | X |
| **VOD** (student, 신규) | O | O | **O** | **X** |
| 프로젝트 관리 시스템 | X | O | O | O |

- 서비스는 **기능으로** 나누고, 이용 등급은 `core.service_access`(데이터)로 정한다.
- 배우는 서비스는 위로 갈수록 닫히고, 에이전트에게는 일하는 시스템만 남는다.

### 1-9. DEV_PLAN

- DEV_PLAN은 Phase별 **목표 · 완료 조건 · 기한**만 고정한다. Phase 안의 task 분해·순서·방법은 훈련생 몫(= 문제해결·지시력 훈련).
- 설계 완료와 함께 확정되고, 이후에는 **변경 요청 + 에이전시 승인**으로만 바뀐다.
- 훈련생은 DEV_PLAN을 수정하지 않는다(체크 표시도 안 함 — CODEOWNERS는 파일 단위라 부분 권한 불가). 완료는 **report 존재로 자동 계산**.

### 1-10. 수업료

- 훈련생 수업료는 **6개월 단위 200만 원(부가세 별도)**, 기간은 짧으면 6개월~1년, 길면 2년.
- **프로젝트 관리 시스템은 수업료를 다루지 않는다.** recodemate의 기간제 수강권(결제 상태·정지·만료 안내 기능 보유)으로 별도 관리.
- 두 시스템은 **연동하지 않는다** — 수강권 만료 시 이용 지속 여부는 에이전시가 판단해 직접 처리.
- → **1차 시스템은 돈을 전혀 다루지 않는다.**

### 1-11. 작업 도구

- **Claude Code를 유일한 바이브 코딩 도구로 강제**한다.
- 훈련생이 **Claude Pro 플랜을 본인 부담**으로 구독(등록 조건으로 안내). Pro 사용량 한도로 멈춘 것을 정체로 오판하지 않도록 평가 시 감안.

### 1-12. 소통 · 자료

- 소통: **프로젝트 스레드(비동기) + 작업 단위 코멘트**. 자유 채팅·카카오톡 채널은 두지 않는다. 대화의 결정은 task·변경 요청으로 승격. 외부 채널에서 정한 것은 스레드·문서로 옮겨야 효력(기본 계약에 명시). 즉답 의무 없음(근로자성 위험 방어).
- 알림: 시스템 안 알림 + 이메일.
- 자료 위치: 프로젝트 산출물 = 프로젝트 저장소 / 에이전시 공통 자료 = Organization 공통 저장소(`handbook`) / 고객 제공 자료 = 별도 파일 저장소(`recode-db` Storage 유력, 배정 상태로 접근 제어) / 비밀값 = 비밀 관리 도구.

### 1-13. GitHub

- 프로젝트 저장소는 **에이전시 GitHub Organization** 소유. 시스템이 GitHub App으로 템플릿에서 생성하고, 담당자는 쓰기 권한(관리자 아님)으로 초대. 종료 시 계약에 따라 고객 이전 또는 보관, 권한 회수.
- 현재 `re8code`는 개인 계정 → Organization 신규 생성 필요.
- 비공개 저장소의 브랜치 보호·필수 승인은 유료 플랜(Team)이 필요하고 외부 협력자도 좌석 과금일 수 있음 — **요금표로 확인 필요**.

## 2. 평가

### 2-1. 관점

혼자 작업 = 바이브 코딩. **코드는 AI가 쓴다. 평가는 "AI가 짠 것을 고객에게 책임지고 내놓을 수 있는가"를 본다.** 코드가 딸깍인 것은 괜찮지만 판단이 딸깍이면 안 된다.

### 2-2. 항목 (6개)

| 항목 | 보는 것 |
|---|---|
| A. 결과물 | 요구 충족, 실제 동작, 배포 |
| B. 지시력 | AI가 처리할 크기로 쪼개고 맥락을 주는가 |
| C. 검증력 | AI 결과를 믿지 않고 직접 확인하는가 |
| D. 이해력 | 납품하는 코드를 설명할 수 있는가 — **졸업 과제 심사 때만 구술 확인** |
| E. 통제력 | 범위·설계 이탈 차단, 보안·비밀값, 망가지면 복구 (틀 준수는 E의 수단) |
| F. 소통 · 자기 관리 | 막힘을 제때 알리고 리듬을 유지하는가 |

### 2-3. 척도와 판정

- 점수 합계 대신 **눈금 4단계**: 지도 필요 / 동행 / 위임 / 책임 — 등급과 같은 언어.
- **가장 낮은 항목이 판정을 정한다**(한 항목만 무너져도 실전 사고).
- 관문: 졸업 과제에서 A "납품 가능" + 나머지 전부 동행 이상.
- 시점: Phase PR 심사(중간) + 프로젝트 종료(최종). 모든 평가에 근거 링크.
- **평가 결과는 훈련생에게 공개.**

### 2-4. 지표 — 성장의 객관화

- 훈련생의 핵심 목표는 성장이고, **스스로 성장하고 있다는 자신감**도 객관화된 지표에서 나온다.
- 핵심: **지표로 표현할 수 있는가 + 바이브 코딩 과정에서 시스템이 추출할 수 있는가.** 추출 가능성은 템플릿이 기록을 정해진 형식으로 남기게 하느냐에 달렸다 — 틀을 지키게 하는 장치와 지표를 뽑는 장치는 같은 것.
- 숫자는 판정의 근거 자료이고, 판정(눈금)은 사람이 한다.
- 훈련생에게는 **과거의 나와 비교**(눈금 사다리 · 성장 곡선 · 처음과 지금)만 보여 주고, 다른 훈련생과의 비교·순위는 에이전시 화면에만.
- 훈련생 화면에는 **조작하기 어려운 지표**만: 결함 수, Phase 반려 횟수, **자기 발견율**(리뷰 지적 결함 중 PR "알려진 문제"에 미리 적은 비율), 요구사항 충족률, CI 복구 시간, 소요 기간.
- 에이전시만: 커밋 간격, task 선행 비율, 프롬프트 수, 작업 크기(형식으로 맞출 수 있는 것).
- **문제해결 능력의 성장** = 문제 하나하나의 일생 추적: 스스로 발견 → 빠르게 해결 → 재발 없음 → **학습 고리**(결함 → "나의 규칙" 한 줄 → 이후 같은 유형 결함 소멸).

| 지표 | 추출 |
|---|---|
| 반려 횟수, CI 복구 시간, 소요 기간, 정체, task 선행, 작업 크기, 범위 이탈, 비밀값 위반, 프롬프트 수 | 완전 자동 (git · CI · PR · `.ai-log`) |
| 결함 수, 자기 발견율, 요구사항 충족률 | 반자동 — 리뷰 태그(`[결함]` 등)·PRD 체크리스트 |
| 검증 기록의 충실도, 프롬프트의 질 | 사람 판단 (프롬프트 질의 AI 분류는 보류) |

### 2-5. Phase 심사 흐름

훈련생이 Phase 완료 시 `dev → main` PR(양식: 한 것 · 검증 요약 · 알려진 문제 · 막혔던 지점) → CI → 시스템이 심사 자료 묶음 생성 → 에이전시 승인(병합)/반려(사유). PR 리뷰 = 피드백(GitHub), 평가 = 판정(시스템). 마지막 Phase PR = 프로젝트 종료 평가, 졸업 과제는 + 원본 비교 + 구술 확인.

## 3. 표준 템플릿

### 3-1. 원칙

- **자동화는 기록에, 생각은 사람에게.** 기록·검사·진행률 계산만 자동화하고, 판단 칸(할 것·안 할 것, 검증 결과, 알려진 문제, 결정 이유)은 빈 양식으로 훈련생이 직접 쓴다. 판단 칸은 짧고 구체적인 질문 형태로.
- **"어떻게 일하는가"는 자유, "무엇을 남기는가"만 고정.** 프로젝트 기반이므로 자유도를 최대로 둔다.
- **막는 것은 사고만, 나머지는 기록.** CI 차단은 🔒 문서 무단 수정과 비밀값뿐, 나머지 위반은 경고 + 관찰 기록.
- 고정점 4개: task(할 것·안 할 것) · report(검증) · Phase PR · 대화 기록. **1 task = 1 report** 유지, 1 task = 1 커밋은 두지 않는다.
- AI에게 판단을 통째로 맡겨도 막을 수는 없지만 대화 기록에 보인다 — 처음부터 알린다.

### 3-2. 구조 (초안)

```
project/
├ CLAUDE.md                작업 규칙                    에이전시 🔒
├ docs/
│ ├ PRD.md                 요구사항(기능 목록은 체크리스트)  에이전시 🔒
│ ├ ARCHITECTURE.md        스택 · ADR · 비용              에이전시 🔒
│ ├ DEV_PLAN.md            Phase 목표·완료 조건·기한      에이전시 🔒
│ └ DEVLOG.md              한 줄 인덱스                   훈련생
├ tasks/_TEMPLATE.md       메타 정보 + 할 것/안 할 것      에이전시 🔒
├ report/_TEMPLATE.md      메타 정보 + 검증 결과(필수)     에이전시 🔒
├ .ai-log/                 프롬프트 기록(훅 자동)
├ .claude/settings.json    대화 기록 훅                   에이전시 🔒
├ .claude/commands/        /brief 만                      에이전시 🔒
├ (나의 규칙 파일)          훈련생이 키우는 규칙            훈련생
├ .github/CODEOWNERS, workflows/ci.yml                    에이전시 🔒
└ src/                     코드                          훈련생
```

- 원장 7개 문서 중 CHANGE_DEVICE는 제외, ACCOUNT_COST는 ARCHITECTURE에 합침.
- 템플릿은 스택 무관한 틀만. 스택별 골격·빌드·테스트는 에이전시가 설계 단계에 얹는다(CI도 틀 검사 / 빌드·테스트 분리).
- CLAUDE.md: 작업 흐름(문서 확인 → task → 작업 → **검증** → report → 커밋), 커밋 규칙, 🔒는 변경 요청으로, "안 할 것" 준수, 비밀값 금지. 장비 이동·계정 정리 등 운영 규칙은 뺀다.
- 커스텀 명령은 상태 보기(`/brief`)만. `/task`·`/report`·`/submit`처럼 내용을 생성하는 명령은 두지 않는다(딸깍 방지).
- **대화 기록**: Claude Code 훅 — `UserPromptSubmit`(프롬프트 → 저장소 `.ai-log/`), `SessionEnd`(전체 대화 → 별도 파일 저장소). 커밋은 있는데 대응 기록이 없으면 표시. 기록에도 비밀값 검사. 약관에 고지.
- **나의 규칙 파일**: 훈련생 소유. AI 실수·검증 발견·리뷰 지적에서 "다음부터 이렇게 시킨다"를 한 줄씩. Claude Code가 읽으므로 실제 행동이 바뀌고, 그 성장이 학습 고리 지표가 된다.
- 브랜치: 훈련생은 `dev`에 직접 커밋, `main`은 Phase PR 승인 시 에이전시만 병합.

## 4. 요구사항 (정리본)

> 회의 중 붙인 번호(1~126)를 삭제·수정을 반영해 영역별로 다시 묶었다. **[미결]**은 §5, 2차 이후 범위는 표시.

**프로젝트 등록 · 설계**
- R6. 에이전시가 프로젝트를 등록하면 템플릿으로 저장소가 자동 생성된다(GitHub App, 에이전시 Organization).

- R8. 에이전시가 분할선 위쪽 문서를 작성하고 "설계 완료"가 되어야 배정할 수 있다.
- R9. DEV_PLAN은 Phase별 목표·완료 조건·기한만 고정한다.
- R10. 분할선은 등급 기본값, 프로젝트별로 위로만 조정 가능, 조정 사유를 남긴다.
- R11. 실전 클론은 익명화 절차와 에이전시 확인을 거쳐 훈련 과제 목록에 올리고, 원본 결과물을 비교 기준으로 연결한다(훈련생 비공개). 과제는 반복 배정할 수 있다.
- R12. 본인 기획은 기획 제안 → 에이전시 확정 순으로 진행하고, 제안 원문과 확정 문서의 차이를 남긴다. 결과물 권리는 훈련생, 종료 시 저장소 이전.

**배정 · 권한**
- R13. 훈련생·랜서는 에이전시가 배정한다. 훈련생에게는 훈련 프로젝트만 배정한다.
- R14. 배정에 방식(에이전시 배정/제안 선정/역제안) 칸을 둔다.
- R15. 배정이 확정되면 분할선에 맞춰 저장소 권한(CODEOWNERS·보호 규칙)이 자동 설정되고, 담당자는 쓰기 권한으로 초대된다. 직접 바꾼 설정은 감지한다.
- R16. 종료 시 저장소는 계약·권리에 따라 이전 또는 보관하고 담당자 권한을 회수한다.
- R17. 수강권은 확인하지 않는다(에이전시가 판단해 권한 처리).

**틀 강제**
- R18. 🔒 문서는 변경 요청 + 에이전시 승인으로만 바뀌고, 승인된 변경은 결정 기록(ADR)으로 남는다.
- R19. CI는 🔒 무단 수정과 비밀값만 차단하고, 나머지 위반은 경고 + 관찰 기록.

- R21. 고객 요구 변경은 고객 → 에이전시 → 문서 개정 → 담당자 통보로만 반영한다.

- R26. task·report·PR·PRD는 지표 추출이 가능한 정해진 형식(메타 정보, 고정 칸, 체크리스트)을 갖는다.

- R27. 보드는 저장소 산출물을 읽어 자동으로 채운다.
- R28. 프로젝트 진행률 = 승인된 Phase 수, Phase 안 진행 = 훈련생 task 대비 report 비율.

| `recode-db` | 서비스↔등급 표 갱신(VOD 추가: 학생·훈련생·랜서 O / 에이전트 X), 훈련 서비스·실전 운영 서비스 → 하나의 프로젝트 관리 서비스(계약·정산·민감정보는 별도 스키마), 8단계 `core` 설계 입력 |
| `student` (미생성) | VOD 서비스(이용 등급, 이용료 방식, 영상 호스팅·비용 검토), 학습 콘텐츠·GNB 링크 이관(기존 계획), 학생 단계 관찰 기록을 에이전시 승급 화면에 제공 |
| `recodemate` | 훈련생 6개월 수강권 상품(200만 원 + VAT). 학생 수강권과 기간 겹침 금지(EXCLUDE 제약) 때문에 승급 시 처리 방식 결정 필요 — 학생 수강권 조기 종료 vs 종료 후 시작 |
| 프로젝트 관리 시스템 (미생성) | 이 문서 전체가 출발점(PRD 초안) |

## 7. 만드는 순서

| 단계 | 사용자가 처음 생기는 시점 | 범위 |
|---|---|---|
| **1차** | 훈련생 | 등록·설계·배정·저장소 자동 생성·권한·틀 강제·보드·스레드·파일 공유·평가·성장 화면·졸업 과제 |
| 2차 | 첫 랜서 승급 | 계약(법률 검토·`work` 민감정보 결정 선행), 분할선 이동 |
| 3차 | 랜서 A | 공지 보드 열람·연습 제안, 경력 증명 |
| 4차 | 첫 에이전트 | 제안·선정·역제안 |

1차 한 줄 요약: **훈련생이 에이전시가 설계한 훈련 프로젝트를 정해진 틀 안에서 자유롭게 바이브 코딩으로 수행하고, 에이전시는 저장소에서 자동으로 채워지는 보드로 진행을 보며, 그 기록이 성장 지표와 졸업 과제·관문 심사의 근거로 쌓인다.** 돈도 AI 스태프도 없다.
