# 작업 지시서 — 프로젝트 매니페스트 생성·갱신

> **버전 `v0.26` · 2026-09-12**
> **정본** — `project-registry/tasks/매니페스트-생성-지시서.md`
>
> **이 파일이 레포 루트에 있다면 사본이다.** 내용은 자족적이라 이 파일만으로 실행할 수 있지만,
> **사본은 낡는다.** 시작 전에 정본이 더 새것인지 한 번 확인한다.
>
> ```bash
> # 형제 폴더로 정본에 닿는 경우
> head -3 ../project-registry/tasks/매니페스트-생성-지시서.md   # 버전 줄만 비교
> diff "$PWD/매니페스트-생성-지시서.md" ../project-registry/tasks/매니페스트-생성-지시서.md
> ```
>
> 닿지 않으면 위 버전·날짜를 사람에게 확인받고 시작한다.
> **정본이 더 새것이면 그것으로 다시 받아서 실행한다.** 낡은 사본으로 작업하지 않는다.
>
> 빈말이 아니다 — 2026-09-04에 **이 지시서가 정본과 어긋나** 허용값에 없는 `ai-api`를
> 명시하고 있었고, 두 프로젝트가 그대로 따라 적어 스키마 위반 2건이 났다. 사람의 실수가
> 아니라 **문서가 틀렸던 것**이다.

각 프로젝트 폴더에서 Claude Code를 열고 이 문서를 붙여넣어 실행한다.
목적은 이 레포에 흩어진 md 문서들을 읽어 기계가 읽을 수 있는 `.project-meta.json` 하나를 만드는 것이다.

**이미 `.project-meta.json`이 있으면 갱신 작업이다.** 통째로 새로 쓰지 말고 기존 값을 살린 채
바뀐 것과 빠진 것만 고친다. 사람이 손으로 채워 넣은 `owner_email`·`note`를 덮어쓰지 않는다.

이 문서 하나로 완결된다. 다른 저장소를 참조하지 않아도 된다.

---

## 작업 범위

**이 폴더 안에서만 작업한다.** 다른 프로젝트 폴더나 상위 디렉터리는 건드리지 않는다.

코드는 수정하지 않는다. 생성하는 파일은 `.project-meta.json` 하나뿐이다.

## 절차

### 0단계 — CLI 사전 점검 ★ 가장 먼저 한다

**계정 주소는 문서보다 CLI가 정확하다.** 문서는 낡지만 CLI는 지금 상태를 말한다.
그런데 CLI 로그인은 브라우저 인증이라 **사람만 할 수 있다.**

그래서 본 작업에 들어가기 전에 *"이 레포를 정확히 기록하려면 어떤 CLI에 어느 계정으로
로그인돼 있어야 하는가"*를 먼저 사람에게 알린다. 작업을 다 끝낸 뒤에 묻는 것보다
왕복이 한 번 줄어든다.

> **★ 이 단계는 작업을 멈춘다.** 필요한 CLI 중 **미로그인이 하나라도 있으면** 0-d 보고를
> 터미널에 출력하고 **거기서 턴을 끝낸다.** 사람이 답하기 전에는 1단계로 넘어가지 않는다.
> 로그인은 브라우저 인증이라 사람만 할 수 있고, 로그인 없이 만든 매니페스트는 `owner_email`이
> 비어 있는 채로 저장돼 결국 사람이 다시 열어야 한다 — 그 왕복을 없애려고 이 단계가 있다.
>
> **멈추지 않는 경우는 둘뿐이다** — (1) 필요한 CLI가 전부 로그인돼 있다. (2) 이 레포에
> CLI가 존재하는 provider가 하나도 없다. 이때는 0-d 보고를 출력하고 곧장 1단계로 간다.
>
> **CLI가 아예 없는 서비스**(도메인 등록기관·공개 데이터 API·CDN 등)는 로그인으로 풀리지 않으므로
> 기다리지 않는다. 처음부터 4단계 보고의 질문 목록으로 보낸다.
>
> 2026-09-12까지 이 자리에 *"이 단계는 작업을 막지 않는다"*고 적혀 있었다. 그 결과 실제 세션에서
> 로그인 안내 없이 매니페스트가 만들어졌다. **"막지 않는다"는 "보고를 생략해도 된다"로 읽힌다.**

#### 0-a. 이 레포가 쓰는 provider 목록을 확보한다

| 상황 | 방법 |
|---|---|
| **갱신** (매니페스트가 이미 있음) | 기존 `services[].provider`를 그대로 읽는다 — 정확하다 |
| **신규** (매니페스트가 없음) | 아래 로컬 증거로 추정한다 — 잠정이며, 1단계 문서 수집 후 보정한다 |

#### 0-b. 조회에 쓸 식별자를 로컬 파일에서 찾는다

**로그인이 돼 있어도 "무엇을" 조회할지 모르면 소용이 없다.** 대부분 레포 안에 이미 있다.

| 찾는 것 | 명령 | 얻는 값 |
|---|---|---|
| GitHub 레포 | `git remote get-url origin` | `owner/repo` |
| Firebase · GCP 프로젝트 | `cat .firebaserc` | 프로젝트 ID (`projects.default`) |
| Supabase 프로젝트 | `grep project_id supabase/config.toml` | 프로젝트 ref |
| Vercel 프로젝트 | `cat .vercel/project.json` | `orgId` · `projectId` |
| Cloud Run 서비스 | `cloudbuild.yaml` · `service.yaml` · `Dockerfile` 존재 | 배포 대상 여부 |

`.firebaserc`의 ID가 사람이 못 알아볼 문자열일 수 있다(예: `project-5886ba8c-ca69-49c9-8c7`).
**그래도 그것이 정답이다.** 알아보기 쉬운 이름으로 바꿔 적지 않는다.

#### 0-c. CLI 설치·로그인 상태를 점검한다

먼저 설치 여부를 한 번에 본다.

```bash
for c in gh gcloud supabase firebase vercel aws wrangler; do
  command -v $c >/dev/null 2>&1 && echo "설치됨 $c" || echo "없음   $c"
done
```

그다음 provider별로 아래를 쓴다.

| provider | CLI | 로그인 확인 | 소유자 조회 |
|---|---|---|---|
| `github` | `gh` | `gh auth status` | `gh repo view <owner>/<repo> --json owner` <br> `gh api user --jq '.login, .email'` |
| `gcp-*` | `gcloud` | `gcloud auth list` | `gcloud projects get-iam-policy <ID> --flatten="bindings[].members" --filter="bindings.role=roles/owner" --format="value(bindings.members)"` |
| `firebase` | `firebase` | `firebase login:list` | `firebase projects:list` |
| `supabase` | `supabase` | `supabase projects list` (실패하면 미로그인) | `supabase projects list` · `supabase orgs list` |
| `vercel` | `vercel` | `vercel whoami` | `vercel projects ls` |

**CLI가 존재하지 않는 것** — 도메인 등록기관(닷홈 등 국내 호스팅) · 공개 데이터 API ·
Anthropic · OpenAI · RapidAPI · Google Forms · Discord · CDN 전반.
이들은 처음부터 사람에게 묻는 경로로 보낸다. 로그인을 기다리지 않는다.

**조회 정확도에는 층이 있다. 정직하게 구분한다.**

- `gcloud`의 IAM 정책 조회는 **이메일을 직접 준다.** 가장 확실하다
- `gh`는 레포 소유자를 `re8code` 같은 **계정명/조직명으로** 준다. 이메일이 아니다.
  소유자를 확인한 뒤 `gh api user`로 현재 로그인 계정과 대조해, 일치할 때만 그 이메일을 쓴다
- `firebase`는 `projects:list`에 프로젝트가 **보이는지 여부**로 판단한다.
  보이면 `login:list`의 이메일이 소유 계정 후보다
- `supabase` CLI에는 `whoami`가 없다. 프로젝트가 목록에 보이는지까지만 알 수 있고,
  **계정 이메일은 사람에게 확인해야 한다**

#### 0-d. 결과를 사람에게 제시하고 판단을 받는다

```
[0단계] CLI 사전 점검 — acme-dashboard

  ✓ 로그인됨   gcloud      현재: ops@example.com
                           → GCP 5건 조회 가능
  ✗ 미로그인   supabase    → Supabase 1건 (project_id: acme-dashboard)
  ✗ 미로그인   gh          → GitHub 1건 (acme/acme-dashboard)
  — CLI 없음   naver-finance  → 계정 개념 없음. account_required: false 후보
  — CLI 없음   discord        → 사람에게 확인 필요

  필요한 계정 3개로 보입니다: ops@example.com · dev@example.com · admin@example.com

  ▶ 여기서 멈춥니다. 로그인이 필요한 명령:
      supabase login
      gh auth login

    다음 중 하나로 답해 주세요.
      · 로그인 후 "계속"   → 0-c 부터 다시 점검하고 1단계로 갑니다
      · "이대로 진행"      → 미로그인 항목은 owner_email 을 비워 두고
                             4단계 보고의 질문 목록으로 올립니다
```

> 위는 **형식 예시**다. 실제 주소는 이 레포의 매니페스트와 CLI 조회 결과로 채운다.

**이 보고를 출력한 뒤 사람의 답을 기다린다. 답을 받기 전에 1단계로 가지 않는다.**
미로그인 항목이 0건이면 보고만 출력하고 바로 1단계로 간다.

**사람이 보고 필요한 것만 로그인하면 된다.** 로그인 명령은 제안만 하고 직접 실행하지 않는다 —
브라우저가 열리고 세션이 멈춘다. "계속"을 받으면 0-c의 로그인 확인부터 다시 돌린다 —
사람이 로그인했다고 말한 것과 CLI가 실제로 로그인된 것은 다르다.

#### ★ 로그인 계정 ≠ 소유 계정

**이것이 이 단계에서 가장 조심할 지점이다.**

`gh auth status`가 알려주는 것은 *"지금 이 장비에서 내가 누구로 로그인했나"*이지
*"이 리소스를 누가 소유하나"*가 아니다. **로그인된 계정을 그대로 `owner_email`에 적으면 안 된다.**

한 레포 안에서 서비스마다 계정이 다른 경우가 실제로 흔하다 — GCP는 A 계정, Supabase는 B 계정,
GitHub은 C 계정인 식이다. CLI는 보통 활성 계정이 하나뿐이라, **한 번 로그인으로는 전부 확인되지 않는다.**

그래서 **반드시 소유자 조회 쪽 명령을 쓴다.** 0-c 표의 오른쪽 열이 그것이다.

부수 효과가 하나 있는데 유용하다 — **계정 A로 로그인하면 B 소유 리소스는 조회가 실패한다.**
그 실패 자체가 *"이건 내 다른 계정 것"*이라는 정보다. 실패를 오류로 보고하지 말고
**"이 계정 소유가 아님"으로 해석해 보고한다.**

### 1단계 — 문서 수집

레포 루트와 `docs/`, `.github/` 아래의 md 파일을 모두 읽는다. 스택, 인프라, 외부 서비스, 계정, 비용, 배포에 관한 서술을 찾는다.

`package.json`, `docker-compose.yml`, `.env.example`, `vercel.json` 등 설정 파일도 읽어 참고한다. 다만 이것들은 **참고용**이며 결과 JSON에 그대로 옮기지 않는다 (아래 "코드에서 알 수 있는 것은 넣지 않는다" 참조).

### 2단계 — JSON 생성·갱신

아래 스키마에 맞춰 레포 루트에 `.project-meta.json`을 만든다.
**이미 있으면 기존 값을 살린 채 바뀐 것만 고친다.** 특히 사람이 채워 넣은 `owner_email`은
0단계에서 **다른 값임을 확인했을 때만** 바꾼다. 확인하지 못했다면 그대로 둔다.

### 3단계 — 자가 검증

파일을 다 쓴 뒤 **"완료 전 자가 검증"** 절의 체크리스트를 직접 돌린다. 여기서 걸리는 것을 남겨두면 취합 도구에서 경고로 올라온다.

### 4단계 — 보고

작업 후 다음을 사람에게 보고한다.

1. **★ 계정 확인이 필요한 서비스 목록** — 계정이 존재하는데 `owner_email`을 확정하지 못한 것.
   추측해서 채우지 말고, **"이 서비스는 어느 계정인가"를 사람에게 물어 목록으로 제시한다.**
   이것이 보고에서 가장 중요한 항목이다.
   **0단계 결과에 따라 세 갈래로 나눠 적는다** — 사람이 무엇을 해야 할지가 갈리기 때문이다.

   | 갈래 | 사람이 할 일 |
   |---|---|
   | CLI 로그인만 하면 풀림 | 로그인 후 재지시 (명령을 함께 적는다) |
   | CLI는 있는데 **다른 계정 소유**라 조회 실패 | 어느 계정인지 알려주거나, 그 계정으로 로그인 |
   | **CLI가 없어 영영 안 풀림** (닷홈·공개 API 등) | 값을 직접 알려줘야 한다 |

2. **0단계에서 CLI로 확인한 값** — 문서에 적힌 것과 **달랐다면 반드시 명시한다.**
   낡은 기록을 고친 것이므로 사람이 알아야 한다
3. `null`로 남긴 나머지 필드와 그 이유
4. 문서에서 서로 모순되는 정보를 발견한 경우 그 내용
5. 문서에 언급은 없지만 설정 파일에서 발견된 외부 서비스 (누락 가능성)
6. `.gitignore` 판단 결과 (마지막 절 참조)

## 필드 규칙

### 값이 고정된 필드 (반드시 아래 목록 중 하나)

이 필드들은 여러 프로젝트를 가로질러 묶는 축이다. 표기가 하나만 어긋나면 집계가 갈라진다.
**목록에 없는 값을 창작하지 않는다.** 애매하면 `other`(category) 또는 `tooling`(role)을 쓴다.

| 필드 | 허용값 |
|---|---|
| `project.status` | `production` / `staging` / `development` / `paused` / `archived` |
| `services[].category` | `domain` / `hosting` / `database` / `email` / `cdn` / `ci` / `auth` / `storage` / `analytics` / `payment` / `ai` / `monitoring` / `other` |
| `services[].cost.cycle` | `monthly` / `yearly` / `free` / `onetime` / `usage` / `null` |
| `services[].cost.currency` | `KRW` / `USD` / `null` |
| `services[].criticality` | `high` / `medium` / `low` |
| `stack[].role` | `frontend` / `backend` / `database` / `infra` / `tooling` |

**자주 나는 실수 두 가지.**

- **AI API는 `ai`다. `ai-api`가 아니다.** 서비스 이름에 "API"가 들어가면 손이 먼저 `ai-api`를
  친다. Anthropic·OpenAI 모두 `ai`로 적는다
- **`role`에 `mobile`은 없다.** 모바일 관련은 `frontend`로 적는다

### ★ `owner_email` — 계정이 있는 서비스는 반드시 채운다

**이 값 하나로 "계정별 조회"와 "비상시 복구 경로"가 만들어진다.** 비어 있으면 그 서비스를 잃었을 때
어느 계정으로 복구하는지 알 방법이 없다. 취합 도구는 이것을 `[medium] 계정 미기입` 경고로 띄운다.

**이름이 `account_ref`·`billing_ref`·`recovery_ref`와 비슷하지만 성격이 정반대다.**
`*_ref`는 자격증명 위치를 가리키는 참조라 비워두는 편이 낫지만, `owner_email`은
**로그인 계정 식별자이고 반드시 채우는 값**이다. 비밀번호가 아니다.

`null`로 두어도 되는 것은 **계정이라는 개념 자체가 없는 서비스**뿐이다.

- `category: cdn` — Tailwind Play CDN, jsDelivr, unpkg, gstatic 처럼 URL 로만 쓰는 것
- 로그인 없이 공개 엔드포인트만 조회하는 것 (공개 시세·공시 데이터 등)

**이 경우 `"account_required": false` 를 함께 적는다.** 그래야 "계정이 없는 것"과
"계정을 안 적은 것"이 구분된다. 적지 않으면 취합 도구는 후자로 보고 경고를 띄운다 —
`category: cdn`만 예외로 자동 추론되기 때문이다.

```json
{
  "provider": "naver-finance",
  "display_name": "네이버 금융",
  "category": "other",
  "owner_email": null,
  "account_required": false,
  "note": "로그인 없는 공개 시세 조회. 계정·과금 개념이 없다"
}
```

**그 외에는 전부 채운다.** 특히 다음은 계정 없이 존재할 수 없다 —
호스팅 · DB · 도메인 등록기관 · GitHub · 클라우드 · AI API · 메일 · 결제.

#### 찾는 순서 — CLI가 문서보다 먼저다

1. **0단계의 CLI 소유자 조회** — 지금 상태를 말하므로 가장 정확하다
2. **레포 문서** (`docs/`·`README`·`ACCOUNT*.md`) — 낡았을 수 있다.
   1번과 다르면 **CLI 쪽을 쓰고 그 사실을 보고한다**
3. **사람에게 묻는다** — 위 둘로 안 되면

문서에서도 CLI로도 찾지 못했다면 **`null`로 묻어두지 말고 4단계 보고의 1번 항목에 올려 사람에게 묻는다.**
이것이 "추측하지 않는다" 규칙의 유일한 예외 처리 방식이다 — 추측하지도 않고, 조용히 비우지도 않는다.

**CLI로 확인한 값이라도 로그인 계정을 그대로 베끼지 않는다.** 0단계 §로그인 계정 ≠ 소유 계정 참조.

### `provider` — 소문자 슬러그

공백과 대문자를 쓰지 않는다. `vercel`, `supabase`, `sentry`, `cloudflare`, `aws-s3`, `openai`.
사람이 볼 이름은 `display_name`에 따로 넣는다 (바로 아래 절 참조).

동일 서비스를 프로젝트마다 다르게 적으면 중복 탐지가 실패한다. 확신이 없으면 서비스의 도메인 앞부분을 슬러그로 쓴다.

### `display_name` — 괄호 안에는 **조회 가능한 식별자**를 넣는다

사람이 볼 이름이지만, **다음에 이 레포를 열 사람이 CLI로 조회할 수 있어야 한다.**
괄호 안에 설명문 대신 식별자를 넣으면 0단계가 훨씬 빨라진다.

| | 예 |
|---|---|
| ✅ 좋음 | `"Firebase (business-1e563)"` · `"GitHub (re8code/business)"` · `"Supabase (my-stock)"` |
| ❌ 나쁨 | `"GitHub (저장소 + Pages)"` · `"Firebase (Firestore + Auth)"` |

나쁜 쪽은 **무엇을 조회해야 할지 알 수 없다.** 사용 기능이나 용도는 `note`에 적는다.

0단계에서 식별자를 새로 알아냈다면 **`display_name`을 그 값으로 갱신한다.**

### `criticality` 판단 기준

**문서의 서술이 아니라 "없으면 서비스가 죽는가"로 판단한다.**

- `high` — 없으면 서비스가 죽는다 (호스팅, DB, 인증, 도메인)
- `medium` — 없으면 기능이 일부 손실된다 (모니터링, 메일)
- `low` — 없어도 운영에 지장 없다 (분석, 부가 도구)

폴백이 없는 CDN 은 `high` 다. 죽으면 전 페이지 스타일이 즉시 깨지기 때문이다.

### `cost` — 이 생태계는 금액을 적지 않는다

**요금제는 수시로 바뀌므로 각 서비스 콘솔의 값이 정본이다.** 매니페스트에는 금액 대신
*"무엇이 언제 돈이 되기 시작하는가"* 를 남긴다. `amount: null`이어도 도구는 깨지지 않는다.

| 상황 | 표기 |
|---|---|
| 무료 | `{ "amount": 0, "currency": null, "cycle": "free" }` |
| 종량 과금 (Cloud Run·Anthropic API 등) | `{ "amount": null, "currency": null, "cycle": "usage" }` |
| 확정 지출이 문서에 적혀 있음 | `amount`에 그대로, `cycle`은 `monthly`/`yearly` (연간이면 연 금액 그대로. 월 환산은 도구가 한다) |
| 일회성 | `cycle: "onetime"` |
| 모름 | 전부 `null` |

**종량 과금의 `amount`는 `null`로 둔다.** 미리 적을 수 있는 값이 아니다. 최근 청구액을 적으면
다음 달에 곧바로 거짓이 된다. 대신 `note`에 **지출 상한을 걸어 두었는지**를 적는다 —
이 축에서 가장 쓸모 있는 정보다.

### ★ `free_tier_limit` — 이 생태계에서 실제로 값을 내는 필드

금액보다 *"초과하면 차단인가 과금인가"* 가 중요하다. 무료 서비스라면 이것을 반드시 채운다.

- Firebase Spark → 한도 초과 시 **차단**, 자동 과금 없음
- Cloud Run → 결제 계정이 연결돼 있으면 한도 초과분이 **조용히 청구됨**
- Supabase Free → 7일 미활동 시 자동 일시정지

**"차단"과 "조용히 청구됨"의 차이가 이 필드의 존재 이유다.** 문서에 한도 수치가 없으면
거동만이라도 적는다.

**단, 과금이라는 개념 자체가 없는 서비스는 `null`로 둔다.** 계정도 청구 수단도 없는 공개 CDN
(Tailwind Play·jsDelivr·unpkg·gstatic)이 여기 해당한다. "과금 개념이 없다"를 이 필드에
**서술로 적으면 안 된다** — 취합 도구는 이 필드가 비어 있는지만 보므로, 없다고 적어도
"한도가 있다"로 집계된다. 가용성 리스크는 `note`에 적는다.

## 절대 규칙

### 추측하지 않는다

문서에 없는 값은 **`null`**로 둔다. 그럴듯한 기본값을 채워 넣지 않는다.

특히 **비용은 절대 추정하지 않는다.** "Vercel Pro는 보통 월 20달러"라는 일반 지식으로 채우면,
사람은 그게 실제 청구액인지 추측값인지 구분할 수 없게 되고 전체 합계가 조용히 틀어진다.

**단, `owner_email`은 다르게 처리한다.** 계정이 존재하는 서비스인데 계정 주소를 모르겠다면,
**0단계의 CLI 소유자 조회로 먼저 확인하고**, 그래도 안 되면 `null`로 두고 끝내지 말고
**보고 단계에서 사람에게 물어 목록으로 제시한다.** 추측은 하지 않되 누락을 조용히 넘기지도 않는다.
비어 있는 채로 두면 아무도 그것이 빠졌다는 사실을 모른다.

**CLI 조회는 추측이 아니다.** 실제 소유자를 읽어 오는 것이므로 "추측하지 않는다"에 어긋나지 않는다.
반대로 **로그인된 계정을 소유자 확인 없이 베끼는 것은 추측이다.** 이 구분을 지킨다.

`updated_at`은 오늘 날짜를 넣되, 사람이 검토하기 전이므로 보고 시 "미검증 상태"임을 명시한다.

### 자격증명을 넣지 않는다

이 파일은 커밋될 가능성이 높다. 다음은 어떤 경우에도 JSON에 넣지 않는다.

- 비밀번호, API 키, 토큰, 시크릿, 접속 문자열
- `.env` 파일의 실제 값

`*_ref` 필드에는 **위치를 가리키는 참조만** 넣는다.

- `1password://항목이름`
- `env://VARIABLE_NAME`
- `bitwarden://항목이름`

작업 중 문서나 설정 파일에서 실제 키나 비밀번호를 발견하면, JSON에 넣지 말고 **보고 단계에서 별도로 경고한다.**

### 코드에서 알 수 있는 것은 넣지 않는다

`package.json`의 의존성 목록, lock 파일의 정확한 버전, 개별 라이브러리 목록은 매니페스트에 옮기지 않는다. 취합 도구가 직접 감지한다.

`stack` 배열에는 **선언한 의도**만 적는다. 즉 "무엇을 쓰기로 정했는가"다. 관리형 DB, 선택한 프레임워크, 아키텍처 결정처럼 코드만 봐서는 알 수 없거나 의도가 드러나야 하는 것들이다.

이 구분이 중요한 이유는, 취합 도구가 **선언된 스택과 실제 감지된 의존성을 대조**해서 기록이 낡은 프로젝트를 찾아내기 때문이다. 매니페스트가 코드를 복사한 것이면 이 대조가 무의미해진다.

손으로 유지하는 필드가 적을수록 이 시스템은 오래 간다.

파일을 저장하기 전에 아래를 직접 확인한다. 여기서 걸리는 것은 전부 취합 도구에서 경고로 올라온다.

- [ ] **0단계를 실행하고 그 결과를 사람에게 제시했는가?**
- [ ] **미로그인 CLI가 있었다면, 사람의 답("계속"/"이대로 진행")을 받은 뒤에 1단계로 갔는가?**
      → 답 없이 진행했다면 이 매니페스트는 0단계를 건너뛴 것이다
- [ ] **`owner_email`이 비어 있는 서비스가 있는가?**
      → `category: cdn` 이거나 로그인이 없는 서비스인가? 아니면 보고 1번 항목에 올렸는가?
- [ ] CLI로 확인 가능한 서비스인데 **확인하지 않고** `owner_email`을 문서에서만 베끼지 않았는가?
- [ ] CLI 로그인 계정을 소유자 확인 없이 `owner_email`에 그대로 적지 않았는가?
- [ ] `display_name` 괄호 안이 **설명문이 아니라 조회 가능한 식별자**인가?
- [ ] `category` 값이 전부 허용 목록 안에 있는가? (`ai-api` 를 쓰지 않았는가?)
- [ ] `role` 값이 전부 허용 목록 안에 있는가? (`mobile` 을 쓰지 않았는가?)
- [ ] `provider`가 전부 소문자 슬러그인가? 같은 서비스를 다른 프로젝트와 다르게 적지 않았는가?
- [ ] 무료 서비스에 `free_tier_limit`을 채웠는가? "차단인가 과금인가"가 드러나는가?
- [ ] `cycle: "usage"` 인 항목의 `amount`가 `null` 인가?
- [ ] `criticality`를 문서 서술이 아니라 "없으면 죽는가"로 판단했는가?
- [ ] JSON이 파싱되는가? (`node -e "JSON.parse(require('fs').readFileSync('.project-meta.json','utf8'))"`)

## 마무리 — `.gitignore` 판단

**기본은 커밋이다.** 매니페스트를 `.gitignore`에 넣으면 **다른 장비에서 이 프로젝트가 집계 대상에서
통째로 빠진다.** 매니페스트가 없는 폴더는 추적 대상이 아니기 때문이다. 변경 이력도 남지 않아
"언제 무엇이 왜 바뀌었는지" 확인할 수 없게 된다.

| 저장소 | 처리 |
|---|---|
| **비공개** | **커밋한다.** `.gitignore`에 넣지 않는다 |
| **공개** | `.gitignore`에 추가한다. 계정 이메일이 공개되기 때문이다 |

공개 저장소라 제외했다면 그 사실을 **반드시 보고한다.** 그 프로젝트는 장비를 옮길 때마다
매니페스트를 손으로 복사해야 하고, 그러지 않으면 조용히 집계에서 빠진다.

판단이 서지 않으면 사람에게 묻는다.
